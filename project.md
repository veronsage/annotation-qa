# Проект: Annotation QA v0.2.0

## 1. Паспорт проекта

**Участники:** Бенабдаллах Илья Юссефович, Юрченко Вероника Андреевна  
**Продукт:** Annotation QA — web-сервис, который по разметке от нескольких разметчиков находит объекты датасета с сомнительной разметкой и отправляет их на ручную проверку  
**Планируемый выпуск:** `v0.2.0` (tag в Git)  
**Исходное состояние:** tag `baseline-0.1.0`, commit `84fe4c9`  
**Репозиторий:** https://github.com/veronsage/annotation-qa

### Контекст и пользователи

Когда датасет для компьютерного зрения размечают несколько человек, проверять всю разметку вручную долго и дорого. Идея сервиса в том, чтобы проверять не всё, а только то, где что-то не сходится.

Кто пользуется:

- руководитель разметки загружает картинки, разметку, список разметчиков и правила, запускает анализ;
- проверяющий смотрит очередь и руками проверяет отобранные объекты;
- ML-инженер по отчёту решает, можно ли уже учить модель на этих данных.

Что для них важно. Во-первых, если объект не попал в очередь, пользователь считает его разметку нормальной. Значит, сервис не должен пропускать проблемные объекты, иначе ошибки уйдут в обучение и никто их не заметит. Для нас это самое важное свойство продукта. Во-вторых, картинки и сведения о разметчиках (имя, email, уровень, оценка качества) не должны быть видны посторонним. В-третьих, на одних и тех же данных и правилах отчёт должен получаться одинаковым, и по отчёту должно быть видно, с какими правилами он построен.

### Границы

В проект входят:

- API на FastAPI (`app/main.py`);
- модуль проверок (`app/qa.py`): сопоставление рамок по IoU, согласие по классам, пропущенные объекты, проверки по правилам, оценка разметчиков;
- хранение в SQLite и в файлах (`app/storage.py`);
- страница с очередью (`app/static/index.html`);
- зависимости, тесты, тестовые данные в `samples/`, инструкция запуска.

Не входят:

- сами инструменты разметки (CVAT, Label Studio) и их форматы экспорта;
- обучение моделей;
- хостинг, reverse proxy, TLS, бэкапы;
- SSO и внешние учётные записи;
- работа на больших датасетах под нагрузкой. Проверим только, что слишком большие запросы не принимаются.

### Компоненты, взаимодействия и границы доверия

Пользователь через браузер или curl загружает в API файлы: JSON с разметкой, JSON с правилами, CSV с разметчиками и картинки. API сохраняет их в SQLite и в папку проекта. По запросу модуль `qa.py` строит отчёт, он тоже сохраняется в SQLite. Страница очереди берёт отчёт из API и показывает его в браузере.

```
клиент ──(файлы)──> API ──> qa.py
                     │
                     ├──> SQLite (проекты, разметка, правила, разметчики, отчёты)
                     └──> data/projects/<id>/ (картинки)

PyPI ──(зависимости)──> приложение
```

Где меняется уровень доверия:

1. Между клиентом и API. Все загружаемые файлы считаем недоверенными: разметку делают внешние люди, файлы могут быть битыми или специально испорченными.
2. Между проектами. В одном сервисе хранятся разные проекты, и данные одного не должны быть доступны в другом.
3. Между нашим кодом и зависимостями из PyPI.

Ещё одно место: `item_id` из загруженной разметки выводится на HTML-страницу.

### Активы и существенные риски

- **Актив:** правильность очереди проверки.  
  **Что может произойти:** проблемный объект не попадает в очередь. Например, через правила с нулевыми порогами можно фактически выключить проверки, и по отчёту этого не видно. Или сама логика проверок что-то не ловит.  
  **Почему это существенно:** сервис существует ради этого. Если он пропускает проблемы, он только создаёт ложную уверенность.

- **Актив:** данные разметчиков (имя, email, уровень, оценка).  
  **Что может произойти:** список с контактами и оценками получает тот, кому он не нужен, например человек из другой команды, у которого есть доступ к сервису.  
  **Почему это существенно:** это персональные данные. Оценка качества ещё и влияет на оплату разметчика.

- **Актив:** картинки и разметка заказчика.  
  **Что может произойти:** кто-то читает или подменяет данные чужого проекта.  
  **Почему это существенно:** датасеты часто закрытые, а подмена разметки портит результат анализа.

- **Актив:** доступность анализа.  
  **Что может произойти:** кривой или огромный файл роняет запрос или забивает диск и память.  
  **Почему это существенно:** анализ не проходит, а ошибка 500 ничего не объясняет пользователю.

- **Актив:** состав выпуска.  
  **Что может произойти:** сервис построен на чужих библиотеках (FastAPI, `python-multipart` и др.), и в зафиксированной у нас версии какой-то из них может быть известная уязвимость.  
  **Почему это существенно:** именно эти библиотеки принимают и разбирают файлы, которые загружают пользователи. Если в разборе загрузки есть дыра, её можно задеть простой загрузкой файла в наш сервис, даже если наш собственный код в порядке.

Главное свойство (проблемный объект попадает в очередь) можно проверить тестами на синтетических данных. Недостатки baseline мы уже нашли (раздел 3), поэтому будет что улучшить и с чем сравнить после улучшения.

## 2. Методологическая основа

**Основная рамка:** NIST SP 800-218 SSDF 1.1 (февраль 2022).  
**Дополнительный источник:** OWASP ASVS 5.0.0. Берём из него только требования к проверке входных данных, работе с файлами, контролю доступа и защите данных, то есть к первым двум границам доверия из раздела 1.

### Что нам нужно от рамки

- подходит маленькому web-сервису;
- охватывает весь цикл от требований до выпуска и разбора найденных проблем, а не только тестирование;
- можно взять несколько практик и превратить их в конкретные вещи в репозитории;
- можно сформулировать требования к правильности результата (очереди), а не только к защите от атакующего.

### Какие рамки рассматривали

- **NIST SSDF 1.1.** Выбрали основной. Она небольшая, в ней четыре группы практик (PO, PS, PW, RV), которые покрывают весь цикл, и она не требует конкретных инструментов. Минус в том, что практики сформулированы общо и их надо самим превращать в действия. Это сделано ниже.
- **ГОСТ Р 56939-2024.** Не взяли основным. Сертифицироваться нам не нужно, а процессов в стандарте много, часть пришлось бы формально урезать. 
- **OWASP SAMM 2.** Это модель зрелости. Мы не оцениваем зрелость организации, поэтому основной она не подходит. Возможно, пригодится для плана развития к ЭК2.
- **OWASP ASVS 5.0.0.** Это каталог технических требований, общий процесс он не задаёт. Взяли дополнительным: SSDF говорит, что требования безопасности надо определить, но какие они для web-API, не говорит, а ASVS как раз это закрывает.
- **IEC 62443-4-1.** Не подходит, это стандарт для промышленных систем.

### Как адаптировали

Ниже положения SSDF, которые мы берём, и во что они превращаются у нас.

**PO.1 — определить требования безопасности.** Применимо частично: требования нужны, но только для нашего сервиса, без уровня организации.  
Что делаем: пишем `SECURITY-REQUIREMENTS.md` на 6–10 требований, привязанных к активам из раздела 1. Главное из них: если запись разметки не удалось обработать, её объект обязательно попадает в очередь. Требования к вводу, файлам и доступу берём из ASVS.  
Результат и как проверяем: у каждого требования есть номер и ссылка на тест. Требование, которое нечем проверить, не принимаем.

**PO.2 — роли и ответственность.** Применимо частично: у нас две роли, а не оргструктура.  
Что делаем: распределяем, кто за какую часть продукта отвечает. Pull request не используем: коммитим в `main`, а второй участник просматривает новые коммиты партнёра (обычно в тот же или на следующий день) и оставляет к коммиту комментарий на GitHub: «ок» или что поправить.  
Результат: таблица ответственности в разделе 4 и комментарии к коммитам.  
Как проверяем: перед выпуском проходим `git log baseline-0.1.0..HEAD`, у каждого коммита с изменением кода есть комментарий второго участника.

**PO.4 — критерии проверок.** Применимо полностью. Сейчас критериев нет (разрыв 4), это то, что вводим к выпуску.  
Что делаем: заранее записываем, когда выпуск готов: все тесты проходят, включая новые негативные; у находок `pip-audit` и Bandit высокой критичности есть решение; решение о выпуске записано.  
Результат: чек-лист в `RELEASE.md` и CI-workflow с `pytest`.  
Как проверяем: tag `v0.2.0` стоит на commit с зелёным CI, чек-лист в `RELEASE.md` заполнен.

**PS.1 — защитить код.** Применимо частично: подпись коммитов и артефактов для нас лишняя.  
Что делаем: включаем защиту ветки `main` на GitHub: запрет force-push и удаления ветки. Так уже попавшие в `main` коммиты (и то, что видел партнёр при просмотре) нельзя тихо переписать.  
Как проверяем: попытка `git push --force` в `main` отклоняется, скриншот настроек в `evidence/`.

**PW.1 — учитывать риски при проектировании.** Применимо частично: делаем простую модель угроз.  
Что делаем: для каждой из трёх границ доверия (раздел 1) выписываем, что там может пойти не так: кто-то подсунул кривой файл, увидел чужие данные, подменил зависимость и т.д. Отдельно записываем главную угрозу: сервис показал «всё чисто» там, где не чисто. Для каждой угрозы решаем: закрываем её требованием (и тестом) или осознанно оставляем и объясняем почему.  
Результат: таблица «угроза → что с ней делаем» в `docs/threat-model.md`.  
Как проверяем: в таблице нет угроз без решения.

**PW.4 — использовать надёжные сторонние компоненты.** Применимо частично: библиотеки уже выбраны, остаётся следить за их состоянием.  
Что делаем: перед выпуском проверяем зависимости на известные уязвимости.  
Как проверяем: каждая находка разобрана (исправлено, неприменимо с объяснением или принято с ответственным и сроком).

**PW.7, PW.8 — review кода и тестирование.** Применимо полностью.  
Что делаем: второй участник просматривает новые коммиты партнёра (см. PO.2); пишем негативные тесты для `qa.py` и тесты API на кривой ввод и запросы без ключа.  
Как проверяем: в `SECURITY-REQUIREMENTS.md` напротив каждого требования стоит имя теста; `pytest` в CI зелёный; второй участник сам запускает тесты партнёра с чистого checkout и добавляет хотя бы один свой набор данных.

**RV.1, RV.2 — находить и исправлять уязвимости.** Применимо частично: внешнего канала для сообщений об уязвимостях у нас нет.  
Что делаем: каждая находка становится issue с меткой `security`, оценкой критичности и решением. К исправлению добавляется регрессионный тест.  
Кто: issue заводит тот, кто нашёл. Критичность оценивает тот, кто этот код не писал.  
Как проверяем: к выпуску нет находок без решения.

Что не взяли: PO.3 (цепочка инструментов) только в объёме CI; PO.5 (защищённые среды) не берём, работаем локально; PS.3 (архивировать выпуск, SBOM, lock-файл с хешами) не берём, для учебного выпуска хватает зафиксированных версий в `requirements.txt` и tag; RV.3 (анализ первопричин) упрощаем до регрессионного теста на каждое исправление. Из ASVS не берём разделы про OAuth, внешнюю аутентификацию, WebSocket и криптографию.

Что проверить в текущем состоянии: как обрабатывается кривая разметка, есть ли разделение проектов, есть ли лимиты на размер, как зафиксированы зависимости, как принимаются изменения.

Что решили:

- **Инструменты:** `pytest` и `hypothesis` (правильность очереди, кривой ввод), Bandit (SAST), `pip-audit` (SCA), GitHub Actions (CI). Schemathesis — если останется время.
- **Доступ:** оставляем как есть — один ключ `X-API-Key` на запущенный экземпляр сервиса. Считаем, что один экземпляр запускает одна команда разметки для своих проектов. Отдельные ключи на проект и учётки в этот выпуск не делаем (см. разрыв 2 и принятие риска в разделе 4). Ключ при этом не убираем: без него любой, кто достучится до порта, видит email разметчиков.

При этом изменения партнёра никто специально не смотрит, ветка `main` не защищена, CI нет, требования безопасности, модель угроз и критерии выпуска не записаны. Tag `baseline-0.1.0` поставлен вручную. Что из этого меняем к выпуску, описано в разделе 4.

На чём основан вывод:

Что уже работает нормально:

- на тестовом наборе сервис находит конфликт классов (`img_002`), пропущенный объект (`img_003`), нарушения правил (`img_004`) и объект с одним разметчиком (`img_005`), а нормальный `img_001` в очередь не попадает (O1);
- запись разметки без нужных полей не выкидывается, объект уходит в очередь с проблемой `bad_annotation` (O4). Разметка на несуществующий объект попадает в отчёт в `unknown_items` (O5). Оба случая покрыты тестами;

- имя загружаемого файла обрезается через `basename`, несуществующий проект даёт 404.

### Существенные разрывы

- **Разрыв 1. Правила ничем не ограничены, и в отчёте их не видно.**  
  **Почему важен:** если загрузить правила с нулевыми порогами, получится почти «чистый» отчёт, и по нему нельзя понять, что проверки ослабили. Это напрямую бьёт по главному свойству сервиса: пользователь доверяет очереди, не зная, с какими правилами она построена.  
  **Свидетельство:** O8 (2 объекта в очереди вместо 4); в отчёте есть только `summary`, `annotator_agreement` и `review_queue`, без применённых правил и версии.  
  **Приоритет:** высокий.

- **Разрыв 2. Один ключ API на всех, проекты не разделены.**  
  **Почему важен:** ключ проверяется, но он один на весь сервис. Кто получил ключ для своего проекта, видит все остальные проекты, их данные и email разметчиков. Email при этом отдаётся целиком, хотя проверяющему он не нужен.  
  **Свидетельство:** O3 (с тем же ключом видны оба проекта, у разметчика есть поле `email`); в `app/main.py` проверка ключа одна для всех маршрутов и не связана с `pid`.  
  **Приоритет:** низкий для этого выпуска. Сервис запускается локально одной командой для своих проектов, поэтому разделение проектов не делаем и принимаем риск (раздел 4). Проверяем только, что без ключа ничего не отдаётся.

- **Разрыв 3. Входные данные не проверяются по формату и размеру.**  
  **Почему важен:** битая запись целиком теперь ловится, но битый объект внутри записи (например, bbox из двух чисел) роняет анализ с ошибкой 500. Невалидный JSON тоже даёт 500. Размер загрузки не ограничен, можно забить диск и память.  
  **Свидетельство:** O6 (500 при анализе), O7 (500 при загрузке), O9 (файл 5 МБ принят); `app/qa.py:49` распаковывает bbox без проверки, `app/main.py:64,81,84` читают файл целиком. Отдельно: `item_id` вставляется на страницу через `innerHTML` (`app/static/index.html:23,30`). Возможно, это XSS, но пока не проверяли.  
  **Приоритет:** средний.

- **Разрыв 4. Нет контрольной точки выпуска и контроля зависимостей.**  
  **Почему важен:** изменения партнёра никто не смотрит, «тесты прошли локально» по факту и есть решение о выпуске. Есть ли в используемых библиотеках известные уязвимости, неизвестно.  
  **Свидетельство:** нет CI, `main` не защищена, в `requirements.txt` зафиксированы только прямые зависимости, на уязвимости их никто не проверял.  
  **Приоритет:** средний.

- **Разрыв 5. Оценка разметчиков, похоже, считается неправильно.**  
  **Почему важен:** на тестовом наборе все три разметчика попали в «низкое согласие», хотя в основном они совпадают с большинством. Разметчик теряет очки, когда объект пропустил кто-то другой. Если по этой оценке платят, это несправедливо.  
  **Свидетельство:** O1 (`annotators_low_agreement: [a1, a2, a3]`), условие в `app/qa.py:106`.  
  **Приоритет:** низкий для безопасности, но влияет на доверие к отчёту.

## 4. Целевой Secure SDLC

Схема рассчитана на команду из двух человек. Главный принцип: изменение делает один, просматривает другой. Pull request не используем, чтобы не тормозить работу вдвоём: коммитим в `main`, а просмотр идёт по уже запушенным коммитам. Автор не оценивает критичность находок в своём коде.

**Кто за что отвечает:**

| Участник | Отвечает за | Просматривает |
| --- | --- | --- |
| Бенабдаллах И. | `app/qa.py`, правила, тесты очереди (направление 1), CI | коммиты Юрченко В. |
| Юрченко В. | входные данные API и файлы (направление 2), контроль доступа к API (направление 3), аудит зависимостей (направление 4) | коммиты Бенабдаллаха И. |

### Практики

Обязательно для каждого выпуска:

1. В сообщении коммита пишем, какое требование из `SECURITY-REQUIREMENTS.md` он затрагивает, если затрагивает.
2. Второй участник просматривает новые коммиты партнёра и оставляет комментарий к коммиту на GitHub. Замечания исправляются следующим коммитом.
3. Ветка `main` защищена от force-push и удаления.
4. В CI на каждый push запускаются `pytest`, Bandit и `pip-audit`.
5. Перед выпуском проходим чек-лист `RELEASE.md`, записываем решение о выпуске и только потом ставим tag.

По ситуации:

- обновляем модель угроз, если поменялись API, формат данных, хранение или появилась новая граница доверия;
- прогоняем API по OpenAPI-схеме, если поменялись маршруты или модели запросов;
- проходим руками разделы ASVS, если трогали загрузку файлов, доступ или вывод данных на страницу;
- добавляем тест на правильность очереди, если меняли `qa.py` или формат правил.

### Что остаётся после практик

| Практика | Что остаётся в репозитории |
| --- | --- |
| требования и модель угроз | `SECURITY-REQUIREMENTS.md`, `docs/threat-model.md` |
| просмотр изменений | комментарии второго участника к коммитам на GitHub |
| защита `main` | настройка ветки на GitHub, скриншот в `evidence/` |
| тесты, SAST, SCA | workflow в `.github/workflows/`, отчёты в `evidence/` |
| находки | issues с меткой `security` и решением по каждой |
| решение о выпуске | заполненный `RELEASE.md` и tag `v0.2.0` |

### Контрольные точки

```
коммит → [1. просмотр партнёром] → [2. CI] → ... → [3. выпуск] → tag v0.2.0
                                                        ↑
находка → issue security → триаж → исправление + тест / принятие риска
```

1. **Просмотр.** Коммит с замечанием партнёра считается незакрытым, пока замечание не исправлено следующим коммитом.
2. **CI.** Если CI красный, следующим делом чиним его, новые фичи не добавляем.
3. **Выпуск.** Tag ставим только на commit с зелёным CI, когда все коммиты с прошлого tag просмотрены, чек-лист заполнен и решение записано.

Что блокирует выпуск всегда, без возможности принять риск:

- проблемный или необработанный объект не попадает в очередь (нарушено главное свойство сервиса);
- данные разметчиков или проекта доступны без ключа.

### Исключения, принятие риска и эскалация

- **Исключения.** Если CI не работает не по нашей вине (например, упал GitHub Actions), запускаем те же проверки локально и пишем об этом одну строку в комментарии к коммиту или в `RELEASE.md`.
- **Принятие риска.** Находки низкой и средней критичности можно принять записью в issue: почему принимаем и когда вернёмся. Высокие принимаем только вдвоём и записываем в решение о выпуске. Два пункта из списка выше принять нельзя. Уже принято для `v0.2.0`: один ключ на весь сервис без разделения проектов (разрыв 2).
- **Эскалация.** Если не сошлись в оценке критичности или в решении о выпуске, выпуск откладываем и идём к преподавателю. Пока решения нет, действует более строгая оценка.
- **Ложные срабатывания.** Закрываем с объяснением и ссылкой на код. Отключать правило в инструменте можно только со ссылкой на issue.

### Что успеваем в курсе

Успеваем: требования, модель угроз, защита `main`, просмотр коммитов друг друга, CI с тестами, Bandit и `pip-audit`, тесты на правильность очереди и на кривой ввод, чек-лист выпуска, ограничения на правила.

Оставляем на потом: отдельные ключи на каждый проект, lock-файл с хешами и SBOM, подпись артефактов, Docker-образ и его сканирование, нагрузочное тестирование, регулярная перепроверка зависимостей выпущенной версии, журнал доступа.

## 5. Технологический профиль: направления и черновой план

### Направление 1. Правильность очереди и правила анализа

**Риск:** «чистый» отчёт там, где он не чистый (разрывы 1 и 5).  
**Гипотезы:**

- с разрешающими правилами проверки фактически выключаются, и по отчёту этого не видно (уже видно в O8);
- если генерировать случайные корректные наборы разметки, найдутся случаи, когда конфликт или пропуск не отмечается. Например, группировка рамок может зависеть от порядка разметчиков;
- оценка разметчика занижается из-за пропусков других разметчиков (O1).

**Цель:** проверить, что проблемный объект всегда оказывается в очереди, а по отчёту видно, с какими правилами он получен.  
**Что проверяем:** `app/qa.py` и правила.  
**Этап:** реализация и проверка перед выпуском.  
**Как (предварительно):** негативные тесты на `pytest`, property-based тесты на `hypothesis`, чтение кода.  
**Как проверяем результат:** второй участник запускает тесты с чистого checkout и сам добавляет пару наборов данных, которых автор тестов не видел.  
**Свидетельства:** `tests/security/test_queue.py`, вывод до и после в `evidence/`.  
**Что не покрывает:** правильность самих порогов с точки зрения ML.

### Направление 2. Входные данные API и файлы

**Риск:** падения, забитый диск, внедрение данных на страницу (разрыв 3).  
**Гипотезы:**

- кривой объект внутри разметки и невалидный JSON дают 500 вместо понятной ошибки 4xx (уже видно в O6, O7);
- без лимитов можно забить память и диск (O9);
- `item_id` с HTML внутри выполнится на странице очереди у проверяющего;
- обход каталога через имя файла не работает благодаря `basename`, но это надо подтвердить тестом.

**Цель:** понять и зафиксировать, как API ведёт себя на недоверенном вводе.  
**Что проверяем:** все маршруты загрузки и страницу очереди.  
**Этап:** проверка перед выпуском, потом регрессия в CI.  
**Как:** негативные тесты API на `pytest`, ручные сценарии по ASVS (ввод, файлы), Bandit. Schemathesis по OpenAPI-схеме, если останется время.  
**Как проверяем результат:** второй участник повторяет запуск по README и руками подтверждает или опровергает каждую находку.  
**Что не покрывает:** сервер не декодирует картинки, поэтому уязвимости библиотек обработки изображений сюда не относятся. Нагрузку и инфраструктуру тоже не смотрим.

**Сценарии апробации:**

1. Загрузить корректный JSON и зафиксировать ожидаемое поведение API.
2. Передать невалидный JSON и проверить, что сервис возвращает контролируемую ошибку 4xx, а не 500.
3. Передать объект с некорректным `bbox` и проверить обработку ошибки.
4. Загрузить файл, превышающий установленный допустимый размер, и проверить его отклонение.
5. Передать `item_id` с HTML/JavaScript и проверить, выполняется ли содержимое на странице очереди.
6. Использовать имя файла с `../` и убедиться, что файл не может быть записан за пределами каталога проекта.

Результаты baseline и повторной проверки после изменений сохраняем в `evidence/`, чтобы можно было сравнить поведение до и после.

### Направление 3. Доступ к проектам и данные разметчиков

**Риск:** данные проектов и email разметчиков получает тот, у кого нет ключа (разрыв 2). Разделение проектов между собой в этот выпуск не делаем (риск принят, раздел 4).  
**Гипотезы:**

- все маршруты `/projects/...` без ключа и с неверным ключом отдают 401 (O2 проверял только часть маршрутов);
- страница очереди и Swagger не раскрывают данные без ключа;
- email разметчика отдаётся там, где он не нужен.

**Цель:** подтвердить, что защищённые данные Annotation QA нельзя получить без корректного API-ключа, и определить, какие данные разметчиков API раскрывает авторизованному пользователю.

**Что проверяем:** маршруты `/projects/...`, получение отчётов и данных разметчиков, страницу очереди и Swagger.

**Этап:** baseline-проверка перед выпуском, затем регрессия после изменений.

**Как:** параметризованный тест «каждый маршрут × верный ключ / неверный ключ / без ключа», ручная проверка по разделу ASVS про контроль доступа.

**Сценарии апробации:**

1. Выполнить запрос к каждому защищённому маршруту без `X-API-Key`.
2. Повторить запрос с неверным `X-API-Key`.
3. Повторить запрос с корректным ключом.
4. Проверить получение отчёта и данных разметчиков без ключа.
5. Проверить, какие персональные данные разметчика возвращаются авторизованному пользователю.
6. Проверить, раскрывает ли страница очереди данные до успешной авторизации.

**Ожидаемое поведение:** запросы без ключа и с неверным ключом отклоняются; защищённые данные доступны только после успешной проверки ключа. Разделение пользователей по проектам в `v0.2.0` сознательно не проверяется как требование выпуска, поскольку этот риск принят в разделе 4.

**Как проверяем результат:** тест пишет не тот, кто писал `app/main.py`.

**Что не покрывает:** разделение проектов, управление учётками, SSO, TLS.

### Направление 4. Зависимости и состав выпуска

**Риск:** уязвимые или непредсказуемые версии библиотек (разрыв 4).  
**Гипотезы:** в зафиксированных версиях FastAPI и `python-multipart` или в подтягиваемых ими библиотеках (`starlette`, `pydantic`) есть известные уязвимости, в том числе в разборе загружаемых файлов.  
**Как:** `pip-audit` по установленному окружению, в CI на каждый push.  
**Как проверяем результат:** второй участник повторяет запуск на чистом окружении и разбирает каждую находку: касается ли она нас.  
**Что не покрывает:** неизвестные уязвимости и те, что опубликуют после проверки. Транзитивные версии не зафиксированы (lock-файл отложен), поэтому результат относится к окружению на день проверки.
